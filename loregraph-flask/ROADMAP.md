# LoreGraph — план дальнейшей разработки

Этот документ — отложенные фичи для производственной практики. Каждый блок описан так, чтобы можно было влиться в работу через неделю/месяц без долгого восстановления контекста.

Порядок не строгий. Делать можно в любом, кроме случаев, где явно указана зависимость.

---

## 1. Теги

**Цель.** Свободные метки для статей, не привязанные к категории. Позволяют срезы по сюжету: `#главные_герои`, `#ключевое_событие`, `#артефакты_севера`. Категория отвечает на вопрос «**что это**», тег — на «**как это связано с моим сюжетом**».

**Объём:** ~1 час.

**Что добавить:**

- **Модель** `Tag(id, world_id, name, color, created_at)` + М2М-таблица `article_tags(article_id, tag_id)` (см. [models.py](models.py))
  - `UniqueConstraint('world_id', 'name')` — теги уникальны в пределах мира
  - Цвет опционален (если нужен — пусть наследуется от категории при создании)
- **Роуты в** [routes/articles.py](routes/articles.py):
  - В `autosave` принимать `tags: ['тег1', 'тег2']` — создавать новые на лету, удалять отсутствующие
  - Endpoint `GET /worlds/<id>/tags.json` — автокомплит по существующим
- **UI** в [templates/articles/edit.html](templates/articles/edit.html):
  - Под селектором категории — компактный chips-input (Alpine + fetch к автокомплиту)
  - На карточках в [templates/articles/list.html](templates/articles/list.html) — теги мелким шрифтом под категорией
- **Фильтрация** в `articles.index`: дополнительный query-param `tag=<id>`
- **На графе:** опционально — ободок узла = цвет первого тега. Не приоритет.

**Что предусмотреть:**
- При удалении тега — не удалять статьи (cascade на `article_tags`, не на articles)
- Лимит ~20 тегов на статью (CHECK или клиентская валидация)

## 2. Закладки

**Цель.** Личные «избранные» статьи — быстрый доступ к тем, с которыми работаешь часто. Не делятся с другими (это персональная фича).

**Объём:** ~30 минут.

**Что добавить:**

- **Модель** `Bookmark(id, user_id, article_id, created_at)` с `UniqueConstraint('user_id', 'article_id')`
- **Роут** `POST /articles/<id>/bookmark` — toggle (создать/удалить)
- **Страница** `/bookmarks` — список всех закладок текущего пользователя, сгруппированный по миру
- **UI:** иконка-звёздочка рядом с pin/delete в [templates/articles/edit.html](templates/articles/edit.html). Закрашенная — добавлена в закладки.
- **Навбар:** ссылка «Закладки» в дропдауне профиля

**Что предусмотреть:**
- При удалении статьи закладки исчезают по cascade
- Закладки — кросс-мировые (пользователь видит закладки из всех своих миров на одной странице)

## 3. Версионирование статей

**Цель.** Снимки статьи в моменты редактирования. История изменений + откат («упс, переписал зря»).

Это **есть в исходном ТЗ** — приоритетная фича.

**Объём:** ~1.5 часа.

**Что добавить:**

- **Модель** `ArticleVersion(id, article_id, version_number, title, content_md, field_values, created_at)`
  - `UniqueConstraint('article_id', 'version_number')`
  - `version_number` = 1, 2, 3, ... (автоинкремент в пределах статьи)
- **Логика создания версий** в `routes/articles.py`:
  - Не на каждый автосейв (это раз в 2 секунды — будет мусор)
  - Создавать на: ручное «Сохранить как версию» (новая кнопка) + автоматически раз в ~10 минут, если контент менялся
  - Простой подход: при autosave сохраняем `last_version_at` на сессии/в БД, если прошло >10 мин — создаём версию
- **Страница** `/worlds/<id>/articles/<aid>/versions`:
  - Список версий с датами и превью (первые 200 символов)
  - Кнопки «Просмотреть» (read-only) и «Откатиться» (заменяет текущий контент)
- **UI:** кнопка «История» рядом с pin/delete в редакторе

**Что предусмотреть:**
- Откат не удаляет старые версии — он создаёт новую (т.е. текущее состояние тоже сохранится как версия N+1 перед заменой)
- Удаление статьи каскадно удаляет все её версии
- Лимит хранимых версий (например, 50) — старые удалять автоматически

## 4. Полнотекстовый поиск

**Цель.** Глобальный поиск по содержимому всех статей мира, а не только по названию. Сейчас в [routes/articles.py:index](routes/articles.py) поиск идёт по `title.ilike(...)`.

**Объём:** ~30 минут.

**Подход:** PostgreSQL Full-Text Search через `to_tsvector` + `to_tsquery`. Нативно, без внешних зависимостей.

**Что добавить:**

- **Колонка-индекс** в `articles`:
  ```sql
  -- generated column с FTS-индексом
  ALTER TABLE articles ADD COLUMN search_vector tsvector
    GENERATED ALWAYS AS (
      setweight(to_tsvector('russian', coalesce(title, '')), 'A') ||
      setweight(to_tsvector('russian', coalesce(content_md, '')), 'C')
    ) STORED;
  CREATE INDEX idx_articles_search ON articles USING GIN(search_vector);
  ```
  Делать **руками** через миграцию или просто SQL (или добавить SQLAlchemy выражение в модель — посмотри как это делается через `Computed`).
- **Поиск** в `routes/articles.py`:
  ```python
  q = func.plainto_tsquery('russian', search)
  articles = articles.filter(Article.search_vector.op('@@')(q))
                     .order_by(func.ts_rank(Article.search_vector, q).desc())
  ```
- **UI:** добавить переключатель «по названию / везде» в форме поиска. Или просто показывать находки из контента подсветкой первого совпадения (через `ts_headline`).

**Что предусмотреть:**
- Русский словарь по умолчанию в Postgres есть. Если хочется лучше — поставить расширение `russian_full` или `pgroonga`, но это уже сильно перебор.
- Markdown-разметка в content_md мешает поиску — можно стрипать через `bleach.clean` перед сохранением в search_vector. Тогда вместо generated column — обычное поле, которое обновляется в `autosave`.

## 5. Экспорт мира

**Цель.** Возможность забрать всё содержимое мира в файлы (Markdown + JSON) — на случай ухода или резервной копии. «Никакого vendor lock-in».

**Объём:** ~1-1.5 часа.

**Что добавить:**

- **Endpoint** `GET /worlds/<id>/export` — собирает ZIP-архив:
  ```
  northern-kingdoms-2026-04-28.zip
  ├── world.json              (мета: title, description, дата экспорта)
  ├── categories.json         (все категории с template_fields)
  ├── relations.json          (все связи с лейблами)
  ├── articles/
  │   ├── geralt.md           (markdown статьи + frontmatter с метой)
  │   ├── ciri.md
  │   └── ...
  └── covers/                 (если есть обложки)
      ├── geralt.jpg
      └── ...
  ```
- **Frontmatter** в md-файлах:
  ```markdown
  ---
  title: "Geralt of Rivia"
  category: "Персонаж"
  tags: ["главный герой", "ведьмак"]
  field_values:
    race: "Человек"
    occupation: "Ведьмак"
  pinned: true
  created_at: "2026-04-26T15:30:00Z"
  updated_at: "2026-04-28T12:00:00Z"
  ---

  Содержимое статьи...
  ```
- **Слаги** для имён файлов (через `python-slugify`) чтобы избежать кириллицы в путях.
- **UI:** кнопка «Экспорт» на странице мира (где-то рядом с удалением)

**Что предусмотреть:**
- Обложки могут быть тяжёлыми — проверить размер архива, при >50 МБ можно просто не паковать или предупредить
- Запоминать дату экспорта на стороне клиента (download header)
- В будущем — обратная фича: импорт ZIP. Но это уже отдельный блок.

## 6. Темы оформления

**Цель.** Несколько готовых палитр на выбор — кому-то надоест синий. Кроме того, сейчас приложение только в тёмной теме — можно добавить светлую.

**Объём:** ~1 час (если палитры готовы).

**Подход:** Tailwind поддерживает разные темы через CSS-переменные. Сейчас все цвета жёстко прописаны в [tailwind config внутри base.html](templates/base.html). Перевести их на CSS-переменные:

```css
:root[data-theme="dark-blue"] {
  --bg: #0B0F1A;
  --brand: #3B82F6;
  --brand-violet: #6366F1;
  /* ... */
}
:root[data-theme="dark-green"] {
  --bg: #0F1A14;
  --brand: #10B981;
  --brand-violet: #059669;
}
:root[data-theme="light"] {
  --bg: #F8FAFC;
  --text: #0B0F1A;
  /* ... */
}
```

В Tailwind config:
```js
colors: {
  bg: { DEFAULT: 'var(--bg)' },
  brand: { DEFAULT: 'var(--brand)' },
  // ...
}
```

**UI:** селектор темы в `/profile` (3-4 готовых варианта). Сохранять выбор в `users.theme` (новое поле) или в localStorage. Применять через `<html data-theme="...">`.

**Что предусмотреть:**
- Светлая тема — это много правок: тени, прозрачности, scrollbars. Не стоит спешить.
- Цветные акценты тёмной темы — проще, делается за 30 минут.
- Можно дать пользователю и ручной color picker для собственного бренд-цвета.

## 7. Кроппер изображений

**Цель.** Дать пользователю возможность выбирать область изображения для обложки статьи и аватара профиля. Сейчас изображения отображаются с обычным `object-cover` и центрированием, поэтому для некоторых файлов важная часть кадра может обрезаться.

**Объём:** ~1.5-2 часа.

**Что добавить:**

- **UI-кроппер** при загрузке обложки и аватара. Подходящий вариант: Cropper.js или аналогичная легкая библиотека.
- **Предпросмотр результата** перед сохранением: для обложки в формате примерно `16:9`, для аватара - квадрат/круг.
- **Серверная обработка** через Pillow: принимать координаты кропа, обрезать исходное изображение и сохранять уже подготовленный файл.
- **Ограничение размера** итоговых изображений: обложки до разумного размера, например `1280x720`, аватары до `256x256`.
- **Интеграция с текущими формами** в [templates/articles/edit.html](templates/articles/edit.html) и [templates/profile/edit.html](templates/profile/edit.html), без изменения основной логики статей и профиля.

**Что предусмотреть:**
- Не хранить лишние координаты кропа в БД, если достаточно сохранить уже обрезанное изображение.
- Оставить простой fallback: если JavaScript не загрузился, обычная загрузка изображения всё равно должна работать.
- Для внешних аватаров Google кроппер не применять, пока изображение не загружено пользователем локально.

## Приоритет, моя рекомендация

Если делать что-то одно — **версионирование** (есть в ТЗ + реальная польза).
Если делать пару — **версионирование + теги** (синергия с уже сделанной системой категорий).
Если делать всё — **сначала экспорт** (страховка от потери данных при экспериментах с остальными фичами).

## Технический долг (накопленный)

Не в плане задач, но имей в виду:

- **Миграции БД.** Сейчас используется `db.create_all()` — добавляет недостающие таблицы, но **не изменяет существующие колонки**. Любая правка модели (тип, констрейнт, новая обязательная колонка) требует пересоздания БД (`docker compose down -v`). Перед серьёзным расширением — поставить **Flask-Migrate**: `pip install Flask-Migrate`, добавить `Migrate(app, db)`, прогнать `flask db init && flask db migrate -m "baseline" && flask db upgrade`.
- **Tailwind через CDN.** В консоли браузера warning: `cdn.tailwindcss.com should not be used in production`. Для учебного проекта — норм. Для прода — поставить через npm (`npm i -D tailwindcss postcss`) и собирать локально.
- **Tests.** Нет ни одного теста. Минимум, что стоит добавить — pytest + pytest-flask + несколько тестов на каждый blueprint (auth, worlds CRUD, articles CRUD, RLS-эквивалент: чужой мир недоступен).
- **Production-сервер.** `flask run` — только dev. Для прода — `gunicorn -w 4 'app:create_app()'` или `waitress-serve --listen=0.0.0.0:8000 app:app` под Windows.
- **Картинки.** Загруженные обложки/аватары не оптимизируются — для production стоит resize'ить через Pillow до разумных размеров (например, обложки → max 1280×720, аватары → 256×256).
